# Deployment

- Keep one shared deployment artifact set for the Cloud Server implementation. Do not copy deployment files into `private-development`, `self-hosted`, or `managed` variants; split this scope only when deployment mechanics genuinely differ.
- Keep the operator-selected ingress and its configuration on the host. Deployment artifacts must not configure endpoint access, caller authentication, or Project authorization.
- The Compose topology uses Linux host networking so a configured loopback listener remains on host loopback. Do not add Compose port publication or broaden the application bind address in deployment artifacts.
- Runtime environment files live outside the checkout and image. Never copy `.env` files, SSH material, private-ingress state, or deployment credentials into the build context.
- Run the application as a numeric unprivileged user with a read-only root filesystem, dropped capabilities, bounded logs, and a stop grace period longer than the application shutdown timeout.
- Mount the claim-custody keyring read-only at `/run/secrets/claudian_claim_custody_keyring`, owned `10001:10001` with mode `0400`, only for the server, restore-recovery gate, and `backup`, `verify-backup`, `restore`, and `verify-authority` jobs. Every profile remains unprivileged with dropped capabilities and `no-new-privileges`; migration, export, `resume-delete`, and unrelated jobs do not receive the mount.
- Keep the migration URL in its distinct `CLAUDIAN_CLOUD_POSTGRES_MIGRATION_URL` field. Only migration, clean restore, restore recovery, offline backup, and offline authority verification receive it. Backup and authority verification may use it at the immediate predecessor schema only to enumerate retained tombstone Project IDs transactionally; all Project records remain runtime-credential, forced-RLS reads.
- Git-backed updates reject a dirty checkout, resolve one fetched commit, build an immutable revision-tagged image while the previous container remains available, and restore the previously observed image if the replacement does not become healthy. Git credentials and host-specific build-network configuration remain operator-owned state outside the repository.
- Schema advancement is a write-quiesced one-shot operation after a verified backup. The previous image may restart only before schema advancement or when it explicitly supports the advanced schema; otherwise recovery is fixed-forward or a clean restore.
- Backup verification is a clean restore into a distinct operator-configured Compose Project, PostgreSQL port, environment files, and authority volume. Bind every named volume and Compose container to one stable operator-provisioned restore ownership identity and require the exact label before any destructive `down --volumes --remove-orphans` reset; a populated target with missing, mixed, or different ownership fails closed. Volume/container enumeration or inspection uncertainty also fails closed and returns control to the deployment transaction so a proven predecessor can reopen. Provision that empty target through the bootstrap owner before verification or fallback restore; never reuse or destructively reset the live authority target. Restore-target bootstrap persists only the new database authority identity and leaves the filesystem pair marker absent for the restore journal to publish.
- The deploy wrapper owns one operator-provisioned crash-durable attempt marker outside the checkout and Git directory, and serializes its complete run with an adjacent host-local process lock. The marker binds the verified backup schema, exact producing image, and whether the observed predecessor is proven safe at that schema: `backup-active` permits old-image restart, `schema-forward` fences migration while candidate writes remain closed, and `forward-only` fences an ambiguous candidate start and clears predecessor proof. Backup maintenance may use the candidate image only after its static compatibility probe accepts the observed schema. A later `forward-only` retry first lets the candidate recover and reach readiness; only a failed candidate recovery rotates the backup identity and verifies a fresh backup with an image compatible with the observed schema. Restore and restored-authority verification use the marker's exact producing image; starting the previous runtime remains a separate exact-schema compatibility decision. Remove the exact marker before reopening the previous authority; before opening a clean restored authority, persist `restored-active` and fail closed until a later integration owner explicitly promotes that target.
- The operator schedules `cloud-reconcile-exports` often enough to enforce export TTLs. The one-shot profile receives only the live authority and export artifact root; it never receives claim-custody keys or backup storage.
- Add PostgreSQL and repository volumes only with the implementation that owns their lifecycle and restore contract; do not scaffold disposable storage that could become accidental authority.
- For the local milestone, PostgreSQL 18 by digest and the Cloud authority volume are a paired persistent restart unit. Fresh-volume provisioning is an explicit operator sequence: start PostgreSQL, run the bootstrap-role one-shot service, run the migration-role one-shot service, then start the runtime with runtime credentials only. The bootstrap persists a private pending authority marker before database creation and may only complete that exact interrupted pairing; an existing database with neither the canonical nor pending marker remains a one-sided restore and fails closed. The runtime never receives bootstrap/migration credentials or applies schema.
- Verify the rendered Compose model, build the pinned image, exercise `/livez` and `/readyz` through the host loopback listener, and prove SIGTERM reaches bounded graceful shutdown.
