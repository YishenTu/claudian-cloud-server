# Deployment

- Keep one shared deployment artifact set for the Cloud Server implementation. Do not copy deployment files into `private-development`, `self-hosted`, or `managed` variants; split this scope only when deployment mechanics genuinely differ.
- Keep the operator-selected ingress and its configuration on the host. Deployment artifacts must not configure endpoint access, caller authentication, or Project authorization.
- The Compose topology uses Linux host networking so a configured loopback listener remains on host loopback. Do not add Compose port publication or broaden the application bind address in deployment artifacts.
- Runtime environment files live outside the checkout and image. Never copy `.env` files, SSH material, private-ingress state, or deployment credentials into the build context.
- Run the application as a numeric unprivileged user with a read-only root filesystem, dropped capabilities, bounded logs, and a stop grace period longer than the application shutdown timeout.
- Mount the claim-custody keyring read-only at `/run/secrets/claudian_claim_custody_keyring`, owned `10001:10001` with mode `0400`, only for the server, restore-recovery gate, Project lifecycle-recovery gate, and `backup`, `verify-backup`, `restore`, and `verify-authority` jobs. Every profile remains unprivileged with dropped capabilities and `no-new-privileges`; migration, export, `resume-delete`, and unrelated jobs do not receive the mount.
- Keep the migration URL in its distinct `CLAUDIAN_CLOUD_POSTGRES_MIGRATION_URL` field. Only empty-database initialization, clean restore, restore recovery, and backup verification receive it. Runtime, backup, export, Project recovery, deletion recovery, and authority verification use runtime credentials only.
- Git-backed current-schema updates reject a dirty checkout, resolve one fetched commit, and build an immutable revision-tagged image while the previous container remains available. They may reopen the unchanged previous image only when candidate authority verification fails before any recovery mutation. Before recovery begins, persist one external one-way fence bound to the exact revision, image identity, and maintenance operation; a retry resumes only that candidate, and the fence is removed only after readiness opens. Git credentials and host-specific build-network configuration remain operator-owned state outside the repository.
- Deployment accepts only an empty environment to initialize or an environment already at the candidate's exact current schema. It never advances an existing schema prefix in place; an old or partial environment requires a separately verified clean restore.
- Backup verification is a clean restore into a distinct operator-configured Compose Project, PostgreSQL port, environment files, and authority volume. Bind every named volume and Compose container to one stable operator-provisioned restore ownership identity and require the exact label before any destructive `down --volumes --remove-orphans` reset; a populated target with missing, mixed, or different ownership fails closed. Volume/container enumeration or inspection uncertainty also fails closed. Provision that empty target through the bootstrap owner before verification; never reuse or destructively reset the live authority target. Restore-target bootstrap persists only the new database authority identity and leaves the filesystem pair marker absent for the restore journal to publish.
- The deploy wrapper serializes host-local operation with a crash-recoverable process lock, resolves and builds one immutable candidate image, rejects any non-current existing schema, and starts only that exact image. Its forward-state fence lives outside the checkout and fails closed when malformed or when the exact candidate is unavailable. Clean restore and backup verification use their isolated operator-owned targets and exact producing image; they do not create an in-place schema-upgrade or predecessor-restart path.
- The operator schedules `cloud-reconcile-exports` often enough to enforce export TTLs. The one-shot profile receives only the live authority and export artifact root; it never receives claim-custody keys or backup storage.
- Startup completes private environment restore recovery before Project lifecycle recovery, and completes Project lifecycle recovery before opening the Cloud Server. The Project recovery gate receives the live authority, claim-custody keyring, and writable backup and export artifact roots, but not the environment backup catalog or migration credential. The server does not receive artifact roots.
- Add PostgreSQL and repository volumes only with the implementation that owns their lifecycle and restore contract; do not scaffold disposable storage that could become accidental authority.
- For the local milestone, PostgreSQL 18 by digest and the Cloud authority volume are a paired persistent restart unit. Fresh-volume provisioning is an explicit operator sequence: start PostgreSQL, run the bootstrap-role one-shot service, run the migration-role one-shot service, then start the runtime with runtime credentials only. The bootstrap persists a private pending authority marker before database creation and may only complete that exact interrupted pairing; an existing database with neither the canonical nor pending marker remains a one-sided restore and fails closed. The runtime never receives bootstrap/migration credentials or applies schema.
- Verify the rendered Compose model, build the pinned image, exercise `/livez` and `/readyz` through the host loopback listener, and prove SIGTERM reaches bounded graceful shutdown.
