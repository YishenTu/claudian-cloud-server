# Coordination persistence

## Storage contract

- PostgreSQL owns coordination records; Git owns objects and refs. Persistence code does not invent authorization, admission, lifecycle, idempotency, or recovery policy.
- Every Project-owned relation, primary/foreign key, uniqueness rule, and ordinary index preserves `project_id` locality. Globally unique IDs never replace composite Project constraints.
- The runtime role is separate from migration and repair roles, is not a table owner, has no `BYPASSRLS`, and remains subject to forced RLS where specified. Cross-Project enumeration returns bounded metadata and re-enters ordinary Project scope for work.

## Locking and connections

- One canonical `ProjectLockKey` implementation owns advisory-key derivation. No repository or caller hashes or casts Project IDs independently.
- Database-only mutations use a transaction-scoped advisory lock. Cross-store workflows use the same key as a session-scoped lock on one pinned connection. Row locks occur only afterward and never replace Project admission.
- A pinned connection remains checked out until the session lock is released or the connection is destroyed. It must never return to the pool while holding a lock.
- A development upload admitted under the Project lock atomically hands the pinned session to an attempt-scoped shared advisory lock. Settlement holds the Project lock while acquiring the matching exclusive lock, so no process can begin or outlive publication or staging cleanup.
- Keep ordinary transactions short and never hold one across Git, network, backup-copy, or filesystem work. Preserve explicit ordinary, pinned-lease, and recovery/health connection budgets.

## Migration and recovery enumeration

- The checksum-verified clean-initialization lane is `0001_foundation.sql` through `0011_cloud_project_membership.sql`. It may initialize only an empty database or verify the exact current completed history; a partial prefix is an unsupported old environment and never an in-place upgrade source. Each schema change owns its registry entry, grants, forced-RLS policy, and real PostgreSQL evidence.
- The recovery-candidate catalog contains only operation kind, opaque Project/operation identity, and scheduling timestamps. Enumerate at most 100 rows per stable keyset page; full journals are readable only after re-entering exact forced-RLS Project scope under the canonical Project lock.
- The active-placement catalog contains only the placement lease needed to schedule startup integrity checks. Classifying an activated Project as `recovery-required` removes its catalog entry in the same transaction so one isolated Project cannot fail global startup integrity enumeration. Enumerate at most 100 rows per stable Project-ID page, then re-enter forced-RLS Project scope under the canonical Project lock for Project, membership, and current-placement facts.
- Every nonterminal Project lifecycle journal updates its candidate in the same transaction. Terminal completion or cancellation removes it. Enumeration is idempotent scheduling and never substitutes for the on-demand journal check.
- Target claim hashes and source-retained protected claim envelopes are distinct records. Batch custody and per-Member redemption receipts have separate constraints; batch acknowledgement cannot alter redemption or retention state. Plaintext claims are never persisted or returned by general persistence interfaces.
- Ordinary invitation reservations, digests, protected envelopes, issuance replay, tombstones, and Join recovery facts use membership-owned relations and constraints distinct from transferred claims. Combined active, pending, and reserved membership capacity cannot exceed the package limit; one invitation may be reserved or consumed by only one Join operation.
- Manager claim overrides never rewrite the accepted transfer batch. Positive override generations, terminal history, one active override, protected secret replay, and redemption receipt linkage remain Project-local and forced-RLS; resolution rejects generation-zero and prior override digests whenever any later generation has been recorded. Responsibility offers enforce one current source slot and one current target slot, and role transitions cancel every other prior-generation current offer in the same transaction. Terminal responsibility offers and their exact offer-operation responses remain for 30 days; compaction atomically replaces every retained idempotency identity with a payload-free tombstone before deleting the offer and response payloads, and backup/restore preserves those tombstones.
- LAN-to-Cloud checkpoint validation imports exact portable records into canonical Project relations in one transaction at the target generation with `maintenance` service state and no placement, principal binding, or event. Activation promotes that inactive state and normalizes only a zero Manager-set generation to the Cloud membership protocol's first positive generation; every positive imported generation remains exact. Pre-relinquishment cancellation may remove the stage only under the exact transfer journal and stage digest.
- Leave persists the expected personal-ref OID in the prepared journal before any effect, then persists ordinary membership/principal revocation and its exact former-principal replay locator in one transaction. General Project queries cannot read that locator; only exact former-principal replay or trusted lifecycle recovery may resolve it, and neither path grants ordinary Project authority.
- Removal persists a Project-local recovery journal and candidate before any membership or Git effect. Removal and Leave settlement lock the Project, target membership, manager generation, and any successor offer; cleanup of bindings, accepted and override claims, responsibility offers, target-owned open work, structured mentions, durable result, membership event, and optional succession is one transaction and never inferred from later Git state.
- Backup logical export includes only the accepted profile's operational continuity. Environment restore imports through narrow storage ports but its global journal and phase policy remain outside coordination and outside the Project recovery catalog.
- Backup v3 represents invitation and claim-override custody as one base64url binary frame containing the frame version, retained key version, ciphertext, and authentication tag. PostgreSQL keeps those fields separate; capture and restore use the one coordination-owned codec, reject unknown or malformed frames, never infer a key version from the active key, and never expose these Cloud-only records through export.
- Clean-environment restore creates one migration-role-only private database fence before canonical migrations. The fence binds only the exact restore operation and database authority plus the one-way publication fact; it never becomes a Project catalog or phase owner. Restore database and migration waits are bounded, and caller cancellation terminates the owned connection before a later effect may begin. Restored authority-volume metadata replaces the source backup volume identity with the fence's target identity, while protected-envelope associated data retains its source environment identity. Cleanup may drop canonical state only through the matching unpublished fence, and authority publication advances the fence in the same database transaction as restored placements.
- Backup/export serialization runs inside one read-only repeatable-read Project snapshot. Multi-row reads are byte-budgeted and paged before the PostgreSQL client materializes them, nested collections and the canonical NDJSON stream count against the same configured coordination ceiling, and ceiling exhaustion fails closed without widening the snapshot or heap reservation.
- Deletion preserves one allowlisted non-content partition after Project-content removal: the existing deletion journal/candidate, terminal responder/result, former-principal acknowledgement map, protected unclaimed claim envelopes, acknowledged redemption-receipt replay records, receipt-key facts required by either, and one tombstone. These rows retain the same Project ID, forced-RLS context, phase CAS, and dispatcher; they are not a second catalog and cannot satisfy ordinary Project admission.
- Environment maintenance enumerates retained tombstones through the bounded runtime terminal-continuity catalog, then re-enters exact forced-RLS Project scope to read terminal continuity records. The catalog is trigger-bound to the tombstone, survives responder expiry, grants no ordinary Project authority, and must not recreate a Project or repository placement.
- Durable ordinary collaboration and membership-operation responses share one Project-scoped idempotency-result relation. Secret replay tombstones, compacted membership-operation tombstones, and lifecycle-journal-backed synthetic results remain separate because they have different retention or recovery authority.
- Terminal responder retention expires on acknowledgement/deadline independently of repository deletion progress. Deletion continuity therefore treats the exact responder as optional after expiry; authority-transfer expiry also removes its protected envelopes, redemption receipts, and receipt keys while the tombstone and lifecycle facts remain.
- An authority-transfer terminal responder retains the selected target Member and exact activation-request digest separately from its read-eligible former principals. Terminal status and claim access do not authorize replay of the target-only activation command.
