# Project authority

## Ownership

- This scope is the policy owner for Project admission, membership and role authorization, managed eligibility evaluation, business idempotency, mutation ordering, lifecycle transitions, and cross-store recovery.
- Derive membership from the accepted ingress actor and current Project state. Never trust client or ingress assertions of membership, role, eligibility, service state, or repository placement.
- Business idempotency is scoped to Project membership and operation intent; device/session attribution is audit context, not a separate business actor.
- Transport, PostgreSQL queries, repository paths, and raw Git commands remain behind their owning modules.

## Mutation contract

- A `ProjectMutationRejection` proves negative settlement only after exact retained-result, tombstone, and nonterminal-journal lookup under the canonical Project lane. Emit it only for durable terminal invitation facts or strictly advanced expected generations/revisions; absent rows, future expected values, mutable authorization, and stale prepared journals remain ambiguous. Transport may preserve this nominal evidence but cannot infer it from error codes or diagnostics.
- Every Project mutation enters the same write lane and canonical PostgreSQL advisory-lock key. Before new work, resolve or isolate every non-terminal cross-store journal.
- Cloud Project creation reserves its Project-scoped Git child before acquiring the canonical Project lease and holds both through completion. It advances only through `prepared`, `repository-publication-intent`, `repository-published`, `activated`, and `completed`. `prepared` durably owns the invisible maintenance Project, pending initial Manager, principal binding, inactive placement, exact request identity, and deterministic repository plan. After `prepared`, creation has no cancellation, cleanup, or deletion path; every recovery owner advances the exact plan forward.
- Join reserves its Project-scoped Git child before acquiring the canonical Project lease and holds both through pending membership, exact personal-ref creation, activation, and completion. Every nonterminal Join fences ordinary Project reads and writes until its recovery owner settles it; intermediate personal refs are never interpreted as ordinary active membership state.
- `repository-publication-intent` is durable before Git effects. The repository owner may create or verify only the persisted storage identity, empty commit, protected main, initial Manager personal ref, and publication marker. `repository-published` records those exact verified facts; `activated` atomically exposes Project, membership, binding, placement, and immutable response; `completed` only settles the journal and recovery catalog.
- Ordinary invitations reserve one of the Project's 100 membership slots at issuance and keep invitation identity, protected secret envelope, digest, current state, immutable issuance response, and replay tombstone separate from transferred-membership claims. Plaintext exists only at the issuance or validation boundary, is never logged or exported, and can replay only from its purpose-bound protected envelope before the fixed replay deadline.
- Join converts one exact active invitation reservation into one server-generated pending Member. It advances only through `prepared`, `membership-pending`, `personal-ref-created`, `membership-active`, and `completed`; after `prepared`, retry and recovery may only continue the exact principal, invitation, Member, pinned main, and personal-ref plan forward. It never reactivates an invitation or admits an already bound principal.
- SQL-only invitation, role, and responsibility changes remain inside one Project transaction. Secret expiry is enforced from immutable timestamps in every owning transaction; a background reconciler is cleanup assistance, not semantic authority.
- Imported-claim generation alone is not negative-settlement proof: it restarts for a later import and the current administration request does not bind a transfer identity. Only continuing manager-set or membership revisions may settle those requests negatively.
- Imported claim administration targets only one active unbound imported Member. Generation zero remains the immutable accepted transfer claim, every Manager override is a separate monotonic authority record, and the existing `claimTransferredMembership` owner resolves exactly one effective digest before binding. Reissue may supersede only an active authority, revoked or expired history remains terminal, and plaintext override claims replay only from their purpose-bound envelope before its fixed deadline.
- Manager responsibility is durable SQL state with no Cloud presence prerequisite. Source and target current-offer uniqueness, immutable expiry, exact offer and membership revisions, role mutation, manager-set generation increment, prior-generation offer cancellation, event append, and idempotency result settle in one Project transaction; self-demotion and removal of the final Manager fail closed.
- Removal and Leave reserve the Project-scoped Git child before the canonical Project lease, persist the exact personal-ref OID before membership effects, and recover only forward through membership settlement, exact ref deletion, and completion. Removal is Manager-authorized against another active Member; it revokes all target bindings and claim authorities, cancels target offers, discards target-owned open work, removes structured mentions, and preserves at least one active Manager.
- A final active Manager may Leave only by consuming the exact acknowledged current-generation `manager-leave` offer for one active successor. Successor promotion, leaving-member settlement, manager-set generation increment, prior-generation offer cancellation, credential and claim revocation, work cleanup, immutable response persistence, and event append are one Project transaction. A Project with no active successor cannot be abandoned.
- Revalidate membership, role, service state, expected revisions, expected OIDs, and placement lease at the last boundary before the first irreversible effect.
- Cross-store operations persist a deterministic pre-effect checkpoint, record possible and confirmed progress, use expected-OID CAS, and finalize idempotently. Never infer success from a missing file or lost response.
- Development activation advances only through `publish-intent`, `repository-published`, `activated`, and `completed`; the Project becomes visible and authoritative only at `activated`. Cancellation advances through `cancel-intent`, `cancelled`, or `recovery-required` and cannot take ownership after `publish-intent`.
- Development bundle staging acquires its process-local gate and atomically hands the canonical Project lock to an attempt-scoped PostgreSQL shared upload fence before streaming. After persisting settlement intent, Project authority closes the local gate, aborts staging, drains the matching exclusive database fence, and only then publishes or deletes the attempt artifact.
- Accept advances only through `prepared`, `result-persisted`, `main-updated`, and `completed`. Its deterministic commit plan is durable at `prepared`, its verified result OID is durable before protected-main CAS, and ordinary cancellation cannot own it afterward.
- Publish resolves recovery before reserving its Project Git child, then acquires the canonical Project lease and validates the personal head through the reservation-owned capability. If recovery appears between preflight and admission, release the reservation and retry later; never recover while holding Git capacity.
- Accept reserves its Project-scoped Git child before acquiring the canonical Project lease and holds that reservation through inspection and settlement. Do not acquire Git capacity from inside the lease: receive-pack uses the same capacity-before-lease order, and inversion can deadlock the Project.
- Backup and export reserve both the Project-scoped Git child and the bounded coordination heap slot before acquiring the canonical Project lease. They hold both through the repeatable logical snapshot, bundle capture, immutable publication, and retained-artifact verification; lease cleanup cannot prevent either reservation from being released. Recovery uses immutable phase-owned staging facts rather than current process build metadata. The five-minute attempt deadline is derived from the durable journal creation time and survives restart; deadline and expired pre-publication recovery both advance through exact cancellation cleanup under a fresh signal. Publication is the one-way boundary after which recovery verifies and completes forward independently from delivery expiry. Backup then remains under immutable catalog retention, while export passes to a distinct bounded delivery owner that removes its exact artifact after success, cancellation, or TTL expiry. A terminal journal or published Project checkpoint never claims restore verification or a complete backup.
- Leave, Retire, authority-transfer completion that creates deletion intent, and deletion reserve their Project-scoped Git child before acquiring the canonical Project lease and carry that exact reservation through recovery. Retire and authority-transfer completion prove the exact repository is present before they create deletion intent. The mixed lifecycle dispatcher performs a capacity-free journal preflight, releases the lease, reserves through the owning lifecycle, then re-enters the canonical lane and re-reads the exact journal before any repository effect.
- Receive-pack resolves pending recovery during its capacity-free authorization preflight, then reserves Git capacity and re-enters write admission to close the race. It never invokes recovery while holding its receive reservation.
- The bounded global recovery catalog schedules work but grants no authority. Startup and every on-demand Project admission acquire the canonical Project lock, enter Project scope, and re-read the authoritative journal before recovery, isolation, or new work.
- One mixed recovery dispatcher routes catalog candidates and ordinary write-admission recovery to the exact activation, Accept, transfer, Leave, Retire, checkpoint, or deletion owner. The dispatcher owns no recovery policy, never treats catalog metadata as authority, and rejects an unknown kind with the affected Project isolated.
- Shared authority-transfer status and cancellation enter the Project-authority transfer dispatcher. It selects a direction only from direction-owner reads that have applied their own authorization under the canonical Project lane; transport never reads lifecycle journals for routing. Unknown transfers and unrelated principals remain indistinguishable, and the selected mutation owner reauthorizes before its effect.
- A lifecycle owner may report that an exact nonterminal phase is waiting for external proof. Startup preserves that recovery candidate and continues, while on-demand ordinary write recovery returns `recovery-required`; waiting never terminalizes the journal or reopens Project admission.
- The authority-transfer recovery owner selects a direction only from the canonical lifecycle journal and delegates to that direction's existing coordinator. The selector owns no phase policy; a composition missing an external proof dependency may return waiting, but it must still provide any locally available post-cutover forward recovery. LAN-to-Cloud recovery after `source-relinquished` uses the exact already-verified durable relinquishment proof and local staged checkpoint/publication; it never makes forward progress depend on recontacting the relinquished source.
- Authority transfer advances the target authority generation to exactly `source + 1`. Pre-cutover cancellation must prove the target has not accepted source relinquishment; at or after the durable relinquishment boundary every recovery path is forward-only and source admission remains terminal.
- Project Authority derives the non-overridable exact 30-day transfer expiry only inside the first-create Project transaction. Exact begin replay reuses the stored expiry; composition and transport cannot replace the retention policy.
- Pre-relinquishment cancellation keeps a quiesced source fenced until the exact target has durably invalidated the transfer and removed attempt-owned staging plus any inactive placement. Only that proof permits the same source generation to reopen; absence, timeout, or disconnect is never proof.
- Cloud-to-LAN Manager cancellation persists `cancel-intent` and may return pending status without reopening the source. Only the exact selected target principal may submit the canonical target-signed invalidation and cleanup confirmation; verification and persistence of that exact proof drive `target-invalidated`, `target-cleaned`, source reopen, and terminal cancellation. Cancellation removes only the exact pre-fence Cloud source verifier before `target-cleaned` and preserves the target evidence key for clean restore. Retries replay one frozen proof and stale or contradictory facts leave recovery waiting.
- Presence never binds another Member's target identity. LAN-to-Cloud activation may bind only the source Host through source proof; Cloud-to-LAN staging may bind only the selected target Host. Every other active Member remains imported but unbound until exact claim redemption.
- A pre-cutover claim-batch acknowledgement proves source custody only and never scrubs a claim. Per-Member scrubbing before expiry requires the same former Member to forward an exact target-signed redemption receipt through the old binding.
- One monotonic claim-batch revision is redeemable per transfer. A missing receipt first replays/queries the exact revision and digest; rotation requires authoritative proof that custody did not commit, atomically invalidates every older target hash, and replaces only uncommitted source custody. Timeout or disconnect never authorizes rotation, and a committed revision always replays the same receipt.
- Leave persists the exact protocol request and expected personal-ref OID at `prepared`, then atomically settles ordinary membership admission, every principal mapping and transferred-claim authority, open Request, structured mentions, responsibility offers, optional Manager succession, immutable protocol response, and one bounded former-principal replay record before exact-ref deletion. Former-principal replay admits only the same trusted principal and exact Leave intent/fingerprint; trusted recovery can continue the exact journal without restoring membership or authorizing another operation.
- Leave, Retire, authority transfer, backup, export, and deletion retain explicit operation-owned phase policy behind the shared journal mechanics. An irreversible lifecycle may hand recovery to another kind only by terminalizing the source journal and creating the target journal in one Project transaction; the dispatcher never schedules two nonterminal journals for one Project. Clean environment restore is not a Project operation and never enters this dispatcher.
- Deletion recovery remains authoritative after Project content removal through the same journal and recovery candidate in the allowlisted non-content coordination partition. Terminal responder/result, acknowledgement map, protected unclaimed claims, and the one tombstone may survive there; no Project content, ordinary admission, or second deletion registry may survive.
- Reads may run concurrently only when they cannot expose a mixed authoritative snapshot. Membership changes re-evaluate queued work and event access.

## Lifecycle scope

- Implement only lifecycle operations advertised by the current protocol capability set. `ARCHITECTURE.md` owns the accepted transfer, Leave, Retire, checkpoint, deletion, visibility, cleanup, cancellation, and recovery phase contracts; a changed phase or owner reopens architecture review before code.
- Tests inject failure after every durable phase and prove same-Project exclusion, different-Project progress, exact replay, and fail-closed recovery.
- Creation tests derive the expected empty commit independently, inject failure after every durable phase, prove reservation-before-lease order, preserve invisibility before activation, and reject collision or replay drift without deleting partial repository state.
- Invitation and Join tests prove fixed expiry and retention, protected exact-response replay, tombstone non-reuse, capacity reservation, uniform invalid-secret failures, concurrent single redemption, exact personal-ref CAS, and forward recovery after every durable phase.
- Imported-claim and Manager-role tests prove monotonic highest-recorded generations, one effective redemption authority, exact secret replay/scrubbing, current-offer uniqueness, timestamp-driven expiry, transactionally consumed promotion, concurrent generation/revision exclusion, and final-Manager preservation.
- Removal and Leave tests inject failure after every durable phase, prove exact-ref stale-state rejection, cleanup of every binding/claim/offer/work surface, concurrent manager-set exclusion, former-principal exact replay, final-Manager succession from one acknowledged offer, and forward-only recovery without restoring authority.
